# 项目文档与注释写作规范

## 使用范围与优先级

修改文档、PowerShell/CMD 提示、Python 可见输出、文件夹选择窗口、报告说明或说明性注释时，先确定读者，再使用本规范。用户当前明确要求优先；历史要求用于保持写作一致性，不替代当前任务。

先核对相关代码，再写现有功能。不要把讨论过但未实现的方案写成可操作步骤，也不要因整理说明而改变业务逻辑。本文只规定本项目的写作方式，不规定提交、推送或 PR 的授权。

## 文件与内容的读者

| 文件或内容 | 主要读者 | 应写的内容与口吻 |
|---|---|---|
| `README.md` | 任何一位工具使用者 | 正式使用说明。说明准备条件、打开哪个文件、如何输入或选择、如何查看结果、如何取消和处理常见错误。使用说明书口吻。 |
| `从这里开始.txt` | 首次使用者 | 最短可执行的上手步骤，与实际菜单顺序一致。不要放开发设计和改动记录。 |
| `版本信息.txt` | 工具使用者 | 当前版本、用途、使用入口、说明文档位置和必要的使用限制。不要混入代码重构过程。 |
| 终端提示、窗口标题、命令行帮助、Excel 报告中的说明文字 | 正在操作工具的使用者 | 告诉使用者现在需要做什么、填写什么、选择什么、操作会产生什么结果。适用同一套说明书风格。 |
| 脚本文件开头的操作指南、示例配置或命令旁的使用说明注释 | 查看这些步骤的使用者 | 同样使用说明书口吻，解释输入和步骤，不叙述开发历史。 |
| `P_README.md` | 维护者、开发者和 AI | 基于 README 的开发参考。复制的使用说明保留说明书口吻；新增开发参考部分允许说明字段映射、代码依据、边界、验证和后续设计。 |
| `.agents/skills/project-writing-style/SKILL.md`、`AGENTS.md` | AI 和维护者 | 明确写作规则、适用范围和文档职责，不作为普通使用者的操作入口。 |
| `tests/` 中的说明、函数 docstring 和内部实现注释 | 开发者 | 解释实现原因、输入输出、边界条件及测试所验证的行为。无需把算法和测试步骤写成使用者教程。 |
| 将来新增的架构、接口、测试或设计文档 | 开发者 | 放在明确标注为开发参考的位置，写清现状、依据、方案及验证范围。不要塞入首次上手步骤。 |

同一脚本可能同时含有使用者提示和内部实现注释，应按内容分别处理，不能因为文件是代码文件就把所有可见提示写成开发者口吻。

## 面向使用者的写法

1. 使用简明中文，默认读者没有开发背景。按“准备条件—输入或选择—执行—核对结果”的实际顺序组织步骤。
2. 直接说明动作，例如“请选择需要处理的子表”“请粘贴审核文件的完整路径”。避免“本次修改了……”“实现了……”“已新增……”“方案 A”等开发过程表述。
3. 参数名、文件名和权限名称只有在帮助使用者完成操作时才出现，并说明在哪里取得或填写。不要将函数名、调用栈、实现过程作为正常操作说明。
4. 每个实际需要使用者操作的位置都应有清楚标注，不额外增加确认步骤：

   | 标注 | 使用场景 |
   |---|---|
   | `【需要输入】` | App ID、App Secret、表格链接、文件路径、自定义下载源等内容输入。说明内容来源和必要格式。 |
   | `【需要选择】` | 菜单编号、单选或多选、文件夹选择窗口。说明可选范围、默认值或取消方式。 |
   | `【写入确认】` | 现有填空或审核覆盖的写入确认。先列明目标和数量，再说明输入全部大写 `YES` 执行、其他输入取消。 |
   | `【需要按键】` | 按 Enter 或任意键结束窗口。 |
   | `【操作说明】`、`【链接说明】` | 阅读提示或等待处理的位置；不要让使用者误以为这里需要额外输入。 |

5. 文档中的菜单、提示示例、输入格式和取消行为必须与实际窗口一致。自动步骤不要伪装成需要人工操作的步骤。
6. 正常提示、常见错误和取消说明都应给出易懂的下一步，不用“修改某函数”“查看内部退出码”等开发指令替代操作指导。
7. 避免把未做的验证写成成功事实；开发验证的详细记录放在开发文档或 PR 中。

## 本项目已确定的示例与术语

- 子表名称示例统一为 `子表1（工作簿1）`、`子表2（工作簿2）`。这是说明用名称；运行时展示飞书返回的真实名称，不要求使用者照此改名。
- 链接示例使用简短的虚构内容，例如 `https://example.feishu.cn/base/abc123?table=tbl001&view=vew001`。不要把聊天中的真实企业域名、表格标识、凭据或业务数据复制进示例。
- 链接输入位置保持精简：一行 `【操作说明】` 说明复制包含 `/base/` 的完整链接并给出简短示例，随后是 `【需要输入】` 提示。不要将给 AI 的括号备注输出给使用者，也不要擅自恢复该位置已删去的多段说明。
- 目标多维表格来自 `config.json` 中的 `app_token` 或启动时输入的链接；App ID / App Secret 用于认证，不能描述为自动列出该应用关联的所有多维表格。
- 同一份多维表格切换子表时，网址中的 `table=`、`view=` 可能变化。当前粘贴链接只确定整份表格，子表由工具菜单选择，网页视图筛选不自动带入工具。
- 更换子表的使用说明以现有菜单 5 和“当前选中”显示为准；如用户只要求调整某一处提示，不顺带改变选择逻辑或其他位置的说明。
- Word 文件夹可在电脑上任意选择。不要因文档整理加入“只能使用工具目录内文件夹”的限制。
- 当前字段匹配按固定表头名称进行，不按第几列定位；具体规则记录在 `P_README.md` 的开发参考部分。

## 面向开发者的写法与注释边界

- 开发参考可以使用字段名、函数名、请求结构、配置约束和测试细节；写清它们影响的行为，避免只罗列术语。
- 明确标为“当前实现”“待讨论／尚未实现”“已验证／未验证”。可配置字段映射等后续方向不能混写为现有功能。
- 内部实现注释优先解释为什么这样做、哪些边界必须保留。例如“写入前重新读取旧值，避免覆盖审核期间的修改”。不机械复述赋值语句，不记录“刚新增”“这次修复”等聊天过程。
- 脚本开头的用户操作指南与内部实现注释分开。用户操作指南解释如何使用；内部注释解释程序为什么这样处理。
- 保留已有真实行为、使用范围和测试依据。被否决或尚未落地的安装包、文件夹限制及安全改造，不作为现行功能或固定要求写入文档。

## 完成前核对

1. 是否把内容放在了对应读者的文档中，使用者说明中是否混入开发过程或未来计划？
2. 所有需要输入、选择、确认或按键的位置是否标注清楚，文档与窗口是否一致？
3. 子表示例是否统一，示例链接是否虚构且简短，是否避免真实凭据和业务标识？
4. 当前匹配、子表范围、文件夹选择及写入规则是否与代码一致，规划是否明确标注尚未实现？
5. 如果复制或同步 README 与 P_README，是否保留原说明并将开发补充清楚分隔，是否避免将开发内容反向混入使用者文档？
6. 只修改文档和注释时，核对结构、引用和差异即可，不为低影响文案新增测试，也不顺带改动运行逻辑。
